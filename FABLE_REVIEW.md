## 1. Executive summary

VibePDF is in unusually good shape for a project of this ambition. The load-bearing decisions —
a **per-document actor** serializing all writes, a **global PDFium lock** acknowledging PDFium's
process-unsafety, the **PDFium-renders / lopdf-mutates byte-handoff split**, **snapshot-based
undo**, and **atomic save with round-trip verification** — are correct, consistently applied,
and well-documented in-code. Test discipline is real: 342 Rust test functions across 52
integration files + 359 frontend tests, deterministic fixtures with documented provenance, and
every write path verified against a real PDF.

The risks are not where one would guess. The engine's correctness on *typical* PDFs is strong;
the exposure is on **atypical pages** (rotated pages, CropBox ≠ MediaBox), **non-ASCII text**,
**encrypted documents crossing the save path**, and — dominating everything — **process debt:
every Phase-4 feature (~14 features, 23 `[~]` markers) has shipped without a single in-app
human verification**, plus lingering Phase-2 viewer checks. (A raw `[~]` grep says 59, but
Phase 3's markers are record-keeping bullets under headers verified in the June sweeps — the
*live* debt is Phase 4 + P2 leftovers.) A single afternoon of in-app verification would retire
more risk than any code change in this document.

| Area | Grade | One-line assessment |
|---|---|---|
| Architecture | **A** | Actor + byte-handoff + typed errors: coherent and enforced. |
| PDF write engine | **B+** | Correct on normal pages; rotated/CropBox/Unicode gaps (below). |
| Undo/save/recovery | **B+** | Atomic + verified save; memory-heavy undo; encrypted-save unknown. |
| Frontend | **B** | Clean layering; silent-failure UX in canvas tools; toolbar scaling. |
| Tests | **A−** | Excellent breadth; blind spots mirror the engine gaps. |
| Security posture | **B−** | Offline-first honored; CSP disabled; encryption story deferred. |
| Docs & process | **B−** | Superb in-code docs; doc-vs-reality drift; large `[~]` backlog. |

## 2. What is verifiably right (keep doing this)

- **`save_document`** (`pdf/document.rs`): serialize → temp file *in the destination's own
  directory* (no cross-FS rename) → **re-open and verify** → one-cycle `.bak` → atomic rename.
  This is the textbook implementation of "no silent breakage of existing PDFs."
- **`PDFIUM_LOCK` + `LazyLock<Pdfium>`** (`document.rs`): the comments encode hard-won knowledge
  (PDFium races on global subsystems across *different* documents; `OnceLock` init races). This
  is exactly the kind of institutional memory that survives contributor turnover.
- **The `Edit` trait** (`undo.rs`): apply-returns-inverse makes undo and redo the same operation
  on opposite stacks — minimal surface, unit-tested against `i32`, capped at 100.
- **Typed error chain** (`error.rs` → `invoke.ts`): one enum, stable wire codes, a dedicated
  `PasswordRequired` variant that the UI pattern-matches to mount the password dialog.
- **Fixture provenance** (`tests/fixtures/PROVENANCE.md`): "no mystery PDFs" is enforced;
  fixtures are generated by committed scripts.
- **The hard-won PDFium findings** are captured in code and tests: `FPDFText_SetText` and
  `reset_matrix` work (throwaway-doc + `Manual` regeneration); `FPDFPage_RemoveObject`
  SIGSEGVs → all deletion goes through lopdf content-stream splice, verified by re-extraction.

## 3. Findings — bugs and issues

### 3.1 HIGH — Page decorations ignore `/Rotate` (rotated pages get sideways output)

> **✅ FIXED 2026-07-06 (P4.HF)** — `cos::page_rotation` + `visual_transform`; all three
> writers lay out in visual space and prepend the compensating `cm`. Tested per-angle on the
> new `rotated.pdf` fixture.

**Where:** `pdf/watermark.rs`, `pdf/background.rs`, `pdf/header_footer.rs` (all placement math);
`cos::page_media_box` is rotation-blind by design.

**What:** All Track-D writers compute placement from the unrotated `MediaBox`. A page with
`/Rotate 90` (extremely common in scanned documents and mixed-orientation reports) displays
rotated in every viewer, but our content is drawn in *unrotated* page space — so a "footer"
lands on the left edge running bottom-to-top, a watermark reads sideways, and a header can sit
in the wrong visual corner. The frontend canvas tools do **not** have this bug (their
`screenToPdf` compensates for display rotation); it is specific to the Rust-side decoration
writers, which never read `/Rotate`.

**Why it happens:** `page_media_box` walks `/Parent` for the `MediaBox` but the writers never
consult the (also inheritable) `/Rotate` key, and the `cm` matrices are built assuming the
MediaBox's axes are the visual axes.

**Fix (moderate, contained):** add `pub(crate) fn page_rotation(doc, page_id) -> i32` next to
`page_media_box` (same `/Parent` walk, normalize to {0, 90, 180, 270}); in each writer, prepend
a compensating rotation to the placement `cm` — rotate by `-rotate` about the page centre and
swap effective width/height for 90/270. One shared helper (`rotation_cm(rotate, media_box) ->
[f32; 6]`) keeps the three writers in lockstep. Add a rotated-page fixture (a `generate-*.py`
one-liner setting `/Rotate 90`) and one test per writer asserting the compensated matrix.

### 3.2 HIGH — Non-ASCII text silently corrupts (all text writers, base-14 fonts only)

**Where:** `cos::escape_pdf_string` (documented at `cos.rs:1873`: "Non-ASCII passes through —
base-14 fonts only render the ASCII/WinAnsi range"), used by free-text `/AP`, text boxes,
watermark, header/footer, stamps.

**What:** the dialogs accept any Unicode ("Página 3", "日付", "№", curly quotes, em-dashes), but
the writers emit raw UTF-8 bytes into PDF literal strings rendered with non-embedded Type1
base-14 fonts and no `/Encoding`. Anything outside ASCII renders as mojibake or notdef boxes in
every viewer. The limitation is documented in code, but **it is invisible at the UI**, so to a
user it is silent output corruption — in a product that will be used in many locales.

**Why it happens:** base-14 fonts are referenced, not embedded; a PDF string's bytes are
interpreted in the font's encoding (Standard/WinAnsi), not UTF-8. Correct arbitrary-text support
requires font embedding + a proper `/Encoding` or CID/Type0 with a `/ToUnicode` CMap.

**Fix (staged):**
1. *Now (small):* transcode to WinAnsi where possible (é, ñ, ½, quotes/dashes all fit) in
   `escape_pdf_string`'s callers; **reject** with a typed `InvalidInput` ("this text needs
   characters the built-in fonts can't show yet") for anything outside WinAnsi, and surface the
   error in the dialogs. Silent corruption → loud, honest failure.
2. *Later (the real feature):* a `font_embed.rs` that subsets a system TTF (the
   `font_resolver.rs` scan already locates candidates) into a Type0/CIDFontType2 with
   `/ToUnicode`. That unlocks Unicode across free-text, text box, watermark, header/footer —
   and D5 Bates in non-Latin scripts. This is the single highest-leverage engine investment
   left in Phase 4's orbit.

### 3.3 HIGH — Encrypted document ⇢ save path behavior is unverified (likely silent decryption)

> **✅ RESOLVED 2026-07-06 (P4.HF)** — the pinning test revealed the *other* failure mode this
> section listed as the alternative: `PDFium` **preserves** encryption on save, and our own
> `verify_pdf_reopens(tmp, None)` then rejected the (correctly encrypted) temp file — so
> **encrypted documents could not be saved at all** (`PasswordRequired` on every save). Fixed
> by threading the open password into `save_document` → `verify_pdf_reopens`. Pinned by test:
> save succeeds, the copy still requires the password, `/Encrypt` survives in the trailer. No
> silent decryption exists; no save-time warning is needed. P6's re-encryption scope shrinks
> to "change/remove password" features.

**Where:** `pdf/document.rs::save_document`; opened-with-password flow from P1.B2.

**What:** PDFium's `FPDF_SaveAsCopy` (behind `save_to_bytes`) is documented/known to write the
saved copy **without** the source encryption. If so: open an AES-encrypted PDF with its
password, tap save → the file on disk is now **unencrypted**, silently. (The alternative failure
mode — `verify_pdf_reopens(tmp, None)` failing with `PasswordRequired`, blocking every save of
an encrypted doc — is also plausible and also bad.) There is a fixture (`p1-encrypted.pdf`) and
an open test (`encrypted_open.rs`), but **no test crosses open-encrypted with save**.

**Why it happens:** encryption is a Phase-6 concern, so nothing re-applies a security handler on
save; PDFium doesn't preserve it for us.

**Fix:** (1) *Immediately:* add the missing test — open `p1-encrypted.pdf` with the password,
save to a temp path, assert what comes out (encrypted? decrypted? error?), and pin the current
behavior. (2) *Until P6 lands re-encryption:* if the answer is "silently decrypted," detect
`doc.permissions()`/security-handler presence at open and make save **warn** ("Saving will
remove this file's password protection — continue?"). (3) *P6:* re-encrypt on save via the
planned `security/encrypt.rs`.

### 3.4 MEDIUM — Decorations place against `MediaBox`, ignoring `CropBox`

> **✅ FIXED 2026-07-06 (P4.HF)** — `cos::page_effective_box` (CropBox∩MediaBox); placement
> targets it, the background colour fill deliberately keeps the full MediaBox. Tested on the
> new `cropped.pdf` fixture.

**Where:** `cos::page_media_box` + all three decoration writers; note `resize.rs` deliberately
*removes* Crop/Bleed/Trim/Art boxes, and `split`/`extract` already have a known CropBox carry
bug (BACKLOG "from P2.B4/C3").

**What:** viewers display the `CropBox` (default = MediaBox). Print-ready PDFs routinely have a
MediaBox larger than the CropBox (bleed). For those, a "centred" watermark is centred on the
*sheet*, not the visible page; a header placed `margin` below MediaBox-top can be entirely
outside the visible area — the user sees a header simply not appear.

**Fix (small):** add `page_effective_box` = CropBox intersected with MediaBox (inheritable, same
walk), and use it for *placement* in watermark/background/header-footer. Background's full-page
fill should arguably still fill the MediaBox (behind bleed) — decide and test both. One
fixture with CropBox ≠ MediaBox covers all three writers.

### 3.5 MEDIUM — Silent failure UX: canvas-tool IPC errors go to `console.warn` only

**Where:** every overlay layer: `link-layer.tsx`, `image-add-layer.tsx`, `image-edit-layer.tsx`,
`annotation-layer.tsx`, `free-text-layer.tsx`, `ink/stamp/measure/polygon` layers, plus
`PdfViewer.tsx`'s extract/split/merge/insert handlers (~14 sites).

**What:** if a backend write fails (locked file, malformed page, the 3.2 encoding rejection once
added), the user's click just… does nothing. The dialogs (Watermark/Background/Header-Footer)
show errors properly; the direct-manipulation tools swallow them. The typed
`CommandError` machinery exists end-to-end and is then dropped on the floor at the last hop.

**Fix (small, high value):** a tiny toast store (`state/toast-store.ts` + one `<Toasts/>` mount
in `App.tsx`), and a shared `reportError(err, "Add link failed")` helper that maps
`CommandError.code` → friendly copy. Mechanically replace the `console.warn` catches. This also
future-proofs every feature that starts rejecting input (3.2).

### 3.6 MEDIUM — Undo history can hold ~100 full document snapshots

**Where:** `undo.rs` (`MAX_UNDO_DEPTH = 100`) + `restore.rs` (`RestoreDocEdit { bytes: Vec<u8> }`),
which nearly every edit now uses as its inverse.

**What:** each edit's inverse is a complete serialized copy of the document. A 150 MB scanned
PDF × a 30-edit annotation session ≈ 4.5 GB of heap; the cap bounds it at 100 copies, which for
big files is not a bound that matters. Redo holds snapshots too.

**Why it's this way:** byte snapshots are the only *provably lossless* inverse for structural
edits, and correctness was (rightly) prioritized.

**Fix (incremental):** (1) cheap: compress snapshots (`zstd` level 1 — PDFs with big image
streams still shrink meaningfully, text-heavy ones dramatically); (2) better: cap by **total
bytes** (e.g. 512 MB budget, evicting oldest) instead of count; (3) best: binary-delta the
snapshots (consecutive saves share most bytes — even a naive common-prefix/suffix delta wins
big). All three are contained in `undo.rs`/`restore.rs`; the `Edit` trait doesn't change.

### 3.7 MEDIUM — Latent corruption: `/Contents` as an indirect reference **to an array**

> **✅ FIXED 2026-07-06 (P4.HF)** — `existing_contents` derefs the reference and flattens a
> referenced array; unit-tested against a synthetically constructed ref→array document.

**Where:** `cos::append_page_content` / `prepend_page_content`:
`Ok(Object::Reference(id)) => vec![Object::Reference(*id)]`.

**What:** `/Contents` may legally be a direct stream ref, a direct array, **or an indirect
reference to an array**. In that third shape, the code treats the array ref as if it were a
stream ref and builds `/Contents [ourStream, refToArray]` — an array element pointing at an
array, which is malformed; strict viewers may drop the page content.

**Why it's latent, not live:** in-app, every cos transform runs on bytes freshly produced by
PDFium's `save_to_bytes`, which normalizes `/Contents`. But these are `pub` functions consumed
by 52 integration tests and any future CLI/batch surface operating on raw user bytes — the trap
is armed for exactly the moment the byte source stops being PDFium.

**Fix (5 lines):** on the `Reference` arm, `get_object(id)`; if it resolves to an `Array`, clone
its elements as the base list; if a `Stream`, keep current behavior. Add one fixture-less unit
test constructing that shape in lopdf directly.

### 3.8 MEDIUM — Tauri CSP is `null`

**Where:** `src-tauri/tauri.conf.json` → `app.security.csp: null`.

**What:** the webview runs with no Content-Security-Policy. Today's attack surface is small
(local React bundle, no remote content), but this app *renders hostile input* (PDFs from
anywhere) through PDF.js on the frontend; defense-in-depth matters. A PDF.js escape or an XSS in
any string we render (document title/author metadata is displayed!) currently has an unfenced
webview with IPC access.

**Fix:** set a strict CSP (`default-src 'self'; script-src 'self'; connect-src ipc:
http://ipc.localhost; img-src 'self' blob: data:; style-src 'self' 'unsafe-inline'` — Tailwind
needs the last). Verify PDF.js worker + blob URLs still function; adjust `img-src`/`worker-src`
accordingly. Also audit that metadata strings are rendered as text (React escapes by default —
confirm no `dangerouslySetInnerHTML` anywhere; none found in this audit).

### 3.9 MEDIUM — No Windows CI leg (a declared target platform is never built or tested)

**Where:** `.github/workflows/ci.yml` — check on `ubuntu-latest`, tests on `macos-latest`.

**What:** the vision doc promises Windows/macOS/Linux. Windows is the platform with the spiciest
differences for this codebase: path handling (`sourcePath.split("/")` in three dialogs breaks on
`C:\…` backslash paths — a **concrete latent bug** in `BackgroundDialog`/`WatermarkDialog`
filename display), PDFium binary loading, `std::fs::rename` semantics onto existing files, and
GPU/webview differences. Linux never runs the test suite either (tests only on macOS).

**Fix:** add a `windows-latest` job (fetch-pdfium already scripts the binary; run `npm run check`
+ both suites); fix the filename displays to split on `/[\\/]/`. Consider a matrix
{ubuntu, macos, windows} × {check, test} with the PDF-touching tests allowed to be
macos+windows only if Linux PDFium fetch is the blocker.

### 3.10 LOW — Right/centre text alignment uses an average-glyph-width estimate

**Where:** `cos::font_avg_em` consumed by watermark centring and header/footer centre/right
alignment (documented in BACKLOG).

**What:** `width ≈ size × avg_em × char_count` is wrong per-string for proportional fonts;
"WWW" vs "iii" diverge wildly. Right-aligned dates drift several points; centred titles sit
slightly off. Cosmetic but visible, and D4/D5 will inherit it.

**Fix:** embed the AFM widths for the 14 standard fonts (they are public domain; a 256-entry
`u16` table per font, ~4 KB total, generated by a script into a `font_metrics.rs`). Exact widths
fix watermark centring, header/footer alignment, *and* free-text wrapping estimates in one
change. (Full fix for arbitrary fonts arrives with 3.2's embedding work.)

### 3.11 LOW — Dirty-flag edge cases

**Where:** `actor.rs` worker loop.

**What:** (a) undoing back to the exact saved state leaves `dirty = true` — the app will claim
unsaved changes that don't exist (harmless, slightly erodes trust). (b) `dirty = false` only on
*same-path* save; save-as leaves the (identical) in-memory doc marked dirty against its new
path. (c) Undo/redo of a no-op correctly doesn't dirty — good.

**Fix:** track a saved-generation counter: increment a `generation: u64` on every recorded edit,
remember `saved_generation` on successful save (any path), and derive
`dirty = generation != saved_generation`, with undo/redo decrementing/incrementing. Small,
self-contained in the actor.

### 3.12 LOW — New content streams are written uncompressed

**Where:** `append_page_content`, `prepend_page_content`, `import_page_as_form` (form stream),
markup/free-text `/AP` streams — all `Stream::new(Dictionary::new(), …)` with no filter;
lopdf does not auto-compress.

**What:** text fragments are tiny (noise), but D1b's imported page content can be hundreds of
KB per import, stored raw. Files grow faster than they need to.

**Fix:** one shared `add_flate_stream(doc, dict, bytes)` helper that FlateDecodes bodies above
a threshold (lopdf supports setting the filter + compressed content), used by all writers.

### 3.13 LOW — Decorations are unremovable after save (no marked-content tagging)

> **✅ FIXED 2026-07-06 (P4.HF2)** — `cos::wrap_decoration` wraps every Track-D fragment in
> `/VibePDF << /Kind (…) /Id (uuid) >> BDC … EMC`. Proven by a splice test: the tagged
> watermark is removed by a mechanical operator splice, original content intact, PDFium
> reopens. D4/D5 inherit the tag through the shared writers.

**Where:** all Track-D writers.

**What:** watermark/background/header-footer become anonymous `q…Q` fragments; after save +
reopen there is no way to find "our" watermark to remove or edit it — BACKLOG already notes
"remove watermark" as future work, but nothing is being laid down *now* to make it possible.

**Fix (tiny now, pays later):** wrap each fragment in marked content with a private tag —
`/VibePDFWatermark BMC … EMC` (or `BDC` with a properties dict carrying kind + a UUID). Cost:
two operators per fragment today. Benefit: a future "remove/edit decoration" is a trivial
operator-splice (the exact machinery `delete_text_run`/`delete_image` already have), instead of
a heuristic. Recommend doing this **before** D4/D5 ship so page numbers and Bates stamps are
findable/replaceable from day one — Bates re-numbering after page insertion is a real workflow.

### 3.14 LOW — `collect_refs` recursion on hostile PDFs

**Where:** `background.rs::collect_refs` (D1b closure copy).

**What:** recursion depth is bounded by object-graph depth; cycles are handled (`acc.insert`
guard), but a crafted PDF with a 100k-deep reference chain could overflow the stack in the
actor thread. Low likelihood, but this function runs on user-picked *source* files.

**Fix:** convert to an explicit worklist (`Vec<ObjectId>` stack) — mechanical, ~10 lines.

## 4. Architecture assessment

**The actor model is the right call and is holding.** One thread owns each `PdfDocument`; every
mutation is a message; `PDFIUM_LOCK` covers the cross-document races PDFium's docs don't warn
you about. The cost — all documents serialized through one FFI lock — is invisible at
interactive workloads and only matters for future batch processing (P8), where the fix is a
worker *process* pool, not threads.

**The byte-handoff (PDFium ⇄ lopdf) discipline is the project's crown jewel.** Every lopdf
transform is bytes→bytes with a PDFium reload as the round-trip verifier, so a malformed write
cannot survive into the live document. The `ETq` incident (concatenated `/Contents` needing a
separator) and the ordinal-mapping verify-by-re-extraction pattern show the discipline works —
bugs get caught at the seam, not in the wild.

**Growing pains, honestly named:**
- **`cos.rs` is 3,878 lines** and is now bookmarks + forms + merge + annotations (12 subtypes) +
  text boxes + images + links + shared content-writer infrastructure. It has crossed from
  "module" to "junk drawer with excellent comments." Recommended split (mechanical, no behavior
  change): `cos/outline.rs`, `cos/acroform.rs`, `cos/merge.rs`, `cos/annots/*.rs`,
  `cos/content.rs` (append/prepend/register/escape/media-box), with `cos/mod.rs` re-exporting
  the current names so `docs/04` and call sites stay valid. Do it *before* P5 (forms) — that
  phase will otherwise add another thousand lines to the drawer.
- **`actor.rs` (3,054 lines) is ~40 near-identical message arms.** The
  `record-inverse/dirty/reply` block is copy-pasted forty times. A
  `fn run_edit(edit: Box<dyn Edit<_>>, history, dirty, reply)` helper collapses each arm to
  three lines; better still, a single `Message::ApplyEdit(Box<dyn Edit + Send>)` for the
  homogeneous cases would delete ~1,500 lines, at the cost of losing per-message tracing labels
  (keep `label()` in the trace).
- **Epoch-based re-render** (`bumpEpoch` → all visible pages re-render + re-fetch overlays) is
  simple and correct but re-rasterizes every visible page after every edit. Fine now; when it
  shows up in profiles, the fix is a per-page epoch (the actor knows which pages an edit
  touched — return `changed_pages: Vec<u32>` in the reply alongside `HistoryState`).
- **Doc-vs-reality drift in `docs/04_ARCHITECTURE.md`:** the module tree lists `page.rs`,
  `text.rs`, `form.rs`, `ocr/`, and `security/{encrypt,sign}.rs`, none of which exist; `CLAUDE.md`
  says React 18 + "Tesseract via leptess — bundled" (repo: React **19**; no OCR dep yet). Either
  mark aspirational entries as *(planned, P6/P7)* or prune. In a project whose process leans
  this hard on docs-as-source-of-truth, drift is expensive.

## 5. Test posture — strengths and blind spots

**Strengths:** 342 Rust test fns / 52 files + 359 frontend tests; golden-image render regression
with a bless workflow; per-feature verification artifacts; independent cross-checks against
Apple PDFKit during recent phases; fixture provenance enforced; "tests are not optional for the
PDF engine" honored by every phase.

**Blind spots (each maps to a §3 finding):**
1. **No rotated-page fixture** — nothing exercises `/Rotate` ≠ 0 (→ 3.1).
2. **No CropBox≠MediaBox fixture** (→ 3.4).
3. **No encrypted-open→save test** (→ 3.3) — the single most important missing test in the repo.
4. **No non-ASCII text test** through any text writer (→ 3.2).
5. **No large-file test** — `many-pages.pdf` is 50 tiny pages; nothing measures a 200 MB scan
   through open/edit/undo/save (→ 3.6). A generated-on-demand, gitignored big fixture (the
   `acceptance/` pattern already exists) would cover it.
6. **No fuzz/corpus pass** — the engine parses hostile input via lopdf on user bytes
   (`import_page_as_form` most directly). A weekend `cargo-fuzz` target on
   `add_background`/`import_page_as_form`/`merge_documents`, or a nightly CI loop over a corpus
   (e.g. a vendored slice of pdf-association's stressful-PDFs), would be proportionate.
7. **E2E (`e2e.yml`, WDIO) exists but covers the P1 shell** — none of the Phase 3–4 tools have
   an end-to-end pointer-driven test. Given 59 unverified `[~]` steps, even five happy-path E2E
   flows (open → annotate → undo → save → reopen) would convert standing human debt into CI.

## 6. Security & privacy posture

- **Offline-first: genuinely honored.** No `fetch`/`reqwest`/network call anywhere in source;
  the only declared future exception (Ollama, P8) is spec'd as opt-in. ✅
- **CSP disabled** (→ 3.8). The app renders untrusted PDFs; fence the webview.
- **Encrypted-save unknown** (→ 3.3) — potential *silent* protection-stripping.
- **Path handling:** commands accept absolute paths from the frontend (`image_path`,
  `source_path`, save destinations). In a Tauri desktop app where the user picks files via the
  native dialog this is acceptable, but any future "recent files"/session-restore auto-open of
  attacker-influenced paths should stay read-only and prompt. Worth one deliberate pass when P5
  forms (which can embed file actions) arrive.
- **`security/` module does not exist yet** — correct per roadmap (P6), but the architecture doc
  implies otherwise (→ §4 drift). The CLAUDE.md rule "don't touch security/ without approval"
  currently guards an empty set.
- **Dependency hygiene:** small, justified dependency set (lopdf with default-features off,
  encoder-only `png`); commit messages carry justifications. Recommend adding `cargo audit` /
  `npm audit` (or osv-scanner) as a non-blocking CI step.

| Concern | Today | When it bites | Mitigation |
|---|---|---|---|
| Full-doc snapshot per edit (undo) | fine for <20 MB docs | large scans, long sessions | §3.6 (compress/byte-budget/delta) |
| `bumpEpoch` full re-render | imperceptible | 4K displays + many visible pages | per-page epochs (§4) |
| `prune_dangling_destinations` on every save | no-op fast-path exists | docs with thousands of links | already returns input unchanged when clean — fine |
| One global PDFium lock | invisible interactively | P8 batch | worker processes, not threads |
| Uncompressed new streams | negligible | D1b PDF-page backgrounds | §3.12 |
| cos edits load/save whole doc per operation | ~ms on test docs | 500 MB docs, multi-edit macros | batch API: one load → N transforms → one save (D4/D5 will already want this for "number all pages") |

The one measured budget in the repo (watermark 50 pages < 2 s) came in at **0.12 s** — the
engine is not the bottleneck; memory (§3.6) is the scaling risk, not CPU.

### 9.3 Engine investments (not on the roadmap, recommended)
- **Font embedding + real metrics** (3.2 + 3.10) — unlocks Unicode everywhere, exact alignment,
  OCR text layers, and professional typography. The biggest single upgrade available.
- **Decoration identity via marked content** (3.13) — enables edit/remove/re-stamp workflows
  (Bates re-runs, watermark removal) that Acrobat parity will eventually demand.
- **Incremental save** (PDF's append-only update mechanism) — would make saves O(edit) instead
  of O(document), preserve signatures (P6 prerequisite for signing correctly!), and pair
  naturally with delta-undo (3.6). Large; design doc first.
- **A `vibepdf-cli`** exposing the bytes→bytes engine (watermark/merge/split/bates from the
  shell) — the engine is already shaped for it (every primitive is `pub fn (bytes) -> bytes`),
  it would harden the non-PDFium-normalized input path (3.7), and it's a distribution channel
  the OSS audience loves.
- **Property-based/fuzz testing** for the cos layer (§5.6).
- **Windows CI + signed release pipeline** (§3.9) — the roadmap's "after phase 8" packaging item
  should at minimum get CI now.
