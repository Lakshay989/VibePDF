# Phase 6 — Signing & security (decoupled steps)

> Goal (per `docs/05_ROADMAP.md`): sign PDFs, encrypt them, redact them
> — properly.
>
> **Hard rule from the roadmap:** the security module is the one place
> where Claude does NOT modify code without explicit human go-ahead per
> change. Crypto bugs are silent and dangerous. Each P6 step requires
> a human review pass on the diff before it lands, even when the
> automated tests pass.

## Acceptance demo (from roadmap)

- Sign `tests/fixtures/acceptance/p6-contract.pdf` with a test certificate. Open in Acrobat: signature verified valid, chain shown.
- Redact an SSN from `tests/fixtures/acceptance/p6-document.pdf`. Run `pdftotext` on the result: the SSN does not appear in extracted text.
- Encrypt a PDF with user + owner passwords. Open with the user password: print is blocked. With the owner password: print works.

## Spec coverage

`P6-SEC-001` through `P6-SEC-012` (12 spec lines). Plus 1 infrastructure step.

## Track A — Signature capture & placement

### P6.A1. `[~]` Signature library infrastructure
- **Spec:** infrastructure
- **What:** Persisted in `<app_data_dir>/signatures/`. Each entry: id, type (draw / type / image), bytes, created-at.
- **Test:** `src-tauri/tests/signature_library.rs`.
- **Depends on:** P1.A3 (recents store sets the persistence pattern).

### P6.A2. `[~]` Draw signature
- **Spec:** P6-SEC-001
- **What:** Capture pointer strokes with smoothing; save to library on confirm.
- **Depends on:** P6.A1.

### P6.A3. `[~]` Type signature
- **Spec:** P6-SEC-002
- **What:** Render typed text in selectable handwriting fonts.
- **Depends on:** P6.A1.

### P6.A4. `[ ]` Image signature
- **Spec:** P6-SEC-003
- **What:** Accept PNG (transparent) / JPG / BMP. Threshold-based background removal for JPG/BMP.
- **Depends on:** P6.A1.

### P6.A5. `[ ]` Place signature (stamp or signature field)
- **Spec:** P6-SEC-004
- **What:** Embed as a stamp annotation when there's no signature field; otherwise place into the existing field as a PKCS#7 digital signature (using A6).
- **Depends on:** P6.A2 + A3 + A4, P6.B1 (cert signing).
- **A5a shipped** (`51bdc36`, `dcf4e2e`): the stamp clause only. Reuses
  `ImageStampEdit`, so no new PDF primitive. Clicking a `/Sig` field **declines**
  rather than stamping over it — a picture on a signature widget reads as signed
  to every viewer and is not.
- **A5b outstanding:** the PKCS#7 half. Blocked on B1. The step stays `[ ]` until
  both halves exist.
- **Deferred decision (2026-08-11):** a placed signature lists in the annotation
  panel as **Stamp**, because that is its `/Subtype`. Left as-is on purpose —
  right now it *is* only a picture, and a `signature` annotation kind introduced
  before B1 would have to be revisited anyway to distinguish a signed document
  from a picture of a signature. **Revisit when building B2** (per-signature
  status display), which is where that distinction has to exist regardless.

## Track B — Certificate signing & verification

### P6.B1. `[ ]` Certificate-based signing (PAdES) — all three slices shipped, awaiting the human sweep
- **Spec:** P6-SEC-005
- **What:** Load PKCS#12 / .pfx. SHA-256 hash of byte range → PKCS#7 signed-data → embed in Signature dict. Lock content per signature's permission level. PAdES-compliant by default (LTV-ready).
- **Touches:** `src-tauri/src/security/sign.rs`.
- **Test:** `src-tauri/tests/sign_pades.rs` — sign hello.pdf with a test cert, verify with `pdfsig` or equivalent.
- **Depends on:** P6.A1. **Requires human review before merge.**

**One spec sentence, four subsystems.** Split by what can be verified on its own:

- **B1a-container `[~]` shipped** — `security/sign.rs` + `tests/sign_container.rs`.
  The `/Sig` dict, the `/Contents` placeholder, the `/ByteRange` arithmetic, and
  the incremental save. No cryptography, no new dependencies; identical under
  every option below, which is why it went first.
  - Signing **appends**. The original bytes are an exact prefix of the output
    (`the_original_bytes_are_untouched`), so an existing signature keeps
    covering what it signed.
  - `/ByteRange` is patched **before** hashing, without changing the file's
    length — it sits inside the signed region, so a patch that moved a byte
    would produce a signature that reads as tampering.
  - Signing an already-signed document is **refused** for now, rather than
    patching the first signature's `/ByteRange` and silently breaking it.
  - Invisible field (`/Rect [0 0 0 0]`). A drawn appearance is A5b's business.
- **B1a-crypto `[~]` shipped** — `security/credential.rs` (PKCS#12 → key +
  chain), `security/cms.rs` (detached `SignedData`), `sign::sign_document`.
  Dependencies approved 2026-08-13.
  - **`openssl cms -verify` accepts our signature and rejects a tampered
    document.** That pair is the only test here worth much: everything else
    checks that our code agrees with itself, which a signature computed over
    the wrong bytes would also pass. Signing over a deliberately-wrong digest
    fails the first and not the second — checked by hand.
  - Both `.pfx` flavours work and produce the *same* credential. The legacy one
    shrouds its key with a PKCS#12 PBE, which `pkcs8::EncryptedPrivateKeyInfo`
    cannot even parse (it reads the algorithm as a PKCS#5 scheme), so both go
    through one dispatch that tries `pkcs5` and falls back to RFC 7292.
  - `signing-certificate-v2` is added by hand — the `cms` builder does not, and
    `/ETSI.CAdES.detached` is a claim about which rules the blob follows.
  - **UI wired** (`pdf_sign_document`, `src/app/SignDialog.tsx`, toolbar
    "Sign…"). **Sign-on-export, and necessarily so:** the actor hands out bytes
    by asking `PDFium` to re-serialise, which rewrites every offset — signing in
    place would give a document the next Save silently un-signs, still looking
    signed until somebody checked. The certificate crosses IPC as a *path*, so
    key material never enters a command payload.
  - Kept apart from `SignatureDialog` (P6.A4/A5a), which manages *pictures* of
    signatures. A picture of a signature and a cryptographic signature make very
    different claims; a UI that blurred them would be the most misleading thing
    in the app.
- **B1b `[~]` shipped** — `DocMdpLevel`, the `/Reference` `/SigRef`, and the
  catalog's `/Perms /DocMDP`. Off by default: an ordinary approval signature
  says *this person signed this* and nothing about later changes.
  - **Certification is detection, not prevention**, and the dialog says so.
    Nothing enforces `DocMDP`; a conforming reader that makes a disallowed
    change reports the signature invalid *afterwards*. "Lock" in the spec line
    is the standard's word, not a description of what happens.
  - **Both halves or neither.** A `/Reference` with no catalog entry certifies
    nothing; a catalog entry pointing at a signature with no `/Reference` is
    malformed. Pinned by `certifying_writes_both_halves`.
  - Only the **first** signature may certify — consistent with signing an
    already-signed document being refused.
  - **Watch the name collision:** the catalog's `/Perms` (this) and the
    `/Encrypt` dictionary's `/Perms` (P6.C1's Algorithm 10 block) share a key
    name and have nothing to do with each other. Both live under `security/`.

**Dependency findings (2026-08-13), for whoever picks this up:**

- `p12` 0.6.3 **cannot open OpenSSL-3-default `.pfx`**. It hard-asserts a SHA-1
  MAC (`p12-0.6.3/src/lib.rs:381`) and *panics* rather than erroring; OpenSSL 3
  defaults to SHA-256. Verified against both flavours. Ruled out.
- RustCrypto's `pkcs12` 0.1.0 is DER types only. The working combination is
  `pkcs12` + `pkcs5` (`EncryptionScheme::decrypt`, covers PBES1 and PBES2) +
  `pkcs8`.
- `cms` + `x509-cert` + `rsa` + `sha2` adds **26 crates**; MSRV 1.80 pins
  `x509-cert` to 0.2.5 (0.3 needs 1.85).
- **OpenSSL 3.3.1 is on the dev machine**, so `openssl cms -verify` is an
  independent verifier — the differential check that caught the `/Perms` bug in
  C1. `pdfsig` is not installed (`brew install poppler`).

### P6.B2. `[ ]` Verify signatures on open
- **Spec:** P6-SEC-006
- **What:** For each signature: cryptographically valid? chain trusted? document modified after signing? cert expired? Display per-signature status.
- **Test:** `src-tauri/tests/sign_verify.rs`.
- **Depends on:** P6.B1.

- **B2a `[~]` shipped** — `security/verify.rs`, `verify_signatures(bytes, now)`.
- **B2b `[~]` shipped** — `pdf_verify_signatures`, `use-signatures.ts`,
  `SignatureBanner.tsx`, and the wording rules in `tools/sign/status.ts`.
  - **Verified on open, not on request**: the spec says "WHEN the user opens",
    and a reader who has to go looking for the panel will not look.
  - **Reads the file from disk, not the actor's bytes.** The actor
    re-serialises through `PDFium`, which moves every offset — verifying that
    would report every signature as broken. The same trap that made signing an
    export in B1a, arriving from the other side. Unsaved edits are therefore
    not reflected, which is the truthful thing to report.
  - **The wording is the feature.** Overstate and a reader trusts a forgery;
    understate and they learn to ignore the panel, which costs them the once it
    matters. `status.ts` is pure and separately tested for exactly that: the
    word "trusted" never appears, a changed document and a bad signature get
    different sentences, and a broken certificate outranks everything because
    it makes the *name* unreliable.
  - The signing time is labelled **claimed** — without a timestamp token it is
    whatever the signer's clock said.

**"Chain-trusted" is the one clause we cannot answer, and we say so.** There are
no trust anchors in this codebase and none we can bundle: document signing is
vouched for by Adobe's AATL or the EU trust list, neither redistributable, and
neither the same thing as the TLS root store. `ChainStatus` therefore has **no
`Trusted` variant** — it reports `SelfSigned`, `IssuerNotChecked`, `Incomplete`
or `Broken`. Reporting "trusted" because a chain is internally consistent would
be worse than reporting nothing: every self-signed certificate has an
internally consistent chain of one. Adding a real trust store is its own step,
and needs a decision about where the roots come from.

**A gap the tests found, not confirmed.** The signature commits to the signed
attributes, *not* to the certificate carried beside them — so altering a byte of
the embedded certificate left everything verifying while the displayed signer
name became whatever an attacker chose. `chain_status` now verifies each
certificate against its issuer's key (and a self-signed one against itself), and
`ChainStatus::Broken` says so. The lesson generalises: **a verifier must check
every claim it displays**, not only the one the format is named after.

**Other decisions:**
- Digest and signature are reported **separately**. Editing the document breaks
  the digest and leaves the signature valid; corrupting the signature does the
  reverse. Collapsing them into one boolean throws away the distinction a user
  needs to know what happened.
- `covers_whole_document` is reported rather than treated as failure: appending
  is how a *second* signature is added, so it is a change to surface, not a
  verdict to reach.
- `now` is a parameter, not a clock call — testable expiry, and it lets a caller
  ask "was this valid when signed?".
- Signatures are found **by shape** (`/ByteRange` + `/Contents`), not by walking
  `/AcroForm /Fields`: one we fail to notice is one we silently fail to check.
- Unsupported digests and non-RSA issuers are reported as *unchecked*, never as
  failed. Reporting a chain broken because we cannot read it is its own lie.

## Track C — Encryption & permissions

### P6.C1. `[ ]` Password protect (user + owner, AES-256)
- **Spec:** P6-SEC-007
- **Touches:** `src-tauri/src/security/encrypt.rs`.
- **Test:** `src-tauri/tests/encrypt.rs`.
- **Depends on:** none. **Requires human review.**

### P6.C2. `[ ]` Remove password protection
- **Spec:** P6-SEC-008
- **What:** Requires owner password. Re-save without encryption.
- **Depends on:** P6.C1.
- **Shipped as an export**, mirroring C1: writes an unprotected copy, leaves the
  open document alone.
- **"Requires the owner password" is enforced by lopdf, not by us.** For AES-256
  (R6) it authenticates the owner password and *rejects* the user password. This
  matches the spec by accident rather than design; pinned by
  `requires_the_owner_password_not_the_user_one`.
- **Deliberate narrowing of C1 (2026-08-12):** owner-only protection — a document
  that opens for anyone but is restricted — is now **refused** at encrypt time.
  lopdf cannot load such a file (it tries the empty user password while parsing,
  and its R6 user authentication does not work), so C2 could not undo what C1
  produced. Writing files we cannot unlock is worse than a missing option.
  **Revisit both when lopdf's R6 user-authentication path is fixed.**
- **Known gap:** AES-256 files carrying `/Length` — pypdf writes one — cannot be
  unlocked. Detected and reported by name rather than as a wrong password.

### P6.C3. `[ ]` Set permissions (print / copy / modify / forms / annotate / extract / assemble)
- **Spec:** P6-SEC-009
- **Depends on:** P6.C1.
- **Applied at protect time**, in the same `/Encrypt` dictionary as the
  passwords. There is no "change the permissions on this existing file" path —
  that would be unlock-then-re-encrypt, and is not what the spec line asks for.
- **`/Perms` is derived from `/P`, not passed alongside it.** The permission bits
  are written twice and compared by readers that validate `/Perms`; deriving the
  second from the first makes a mismatch unrepresentable rather than merely
  tested. See `fix_permissions_entry`.
- **High-quality printing (bit 12) follows `print`.** On its own it only selects
  *degraded* printing, which is not a distinction worth a checkbox.
- **Advisory, and the UI says so.** Nothing enforces permissions; `PDFium`
  largely ignores `/P`; and with no distinct owner password anyone who can open
  the file can lift them. Whether any reader honours them is an **Acrobat**
  check on the sweep, not something a test here can answer.

## Track D — Redaction & cleaning

### P6.D1. `[ ]` True redaction (region-based)
- **Spec:** P6-SEC-010
- **What:** (a) Remove text/image content in the region from the content stream — not an overlay; (b) optionally remove or rewrite metadata; (c) verify by extracting text from the saved file that the redacted text is gone.
- **Touches:** `src-tauri/src/security/redact.rs`.
- **Test:** `src-tauri/tests/redact_region.rs` — redact a known string, then `pdftotext` and assert it's missing.
- **Depends on:** P4.A3 (reflow primitive). **Requires human review.**

### P6.D2. `[ ]` Pattern-based redaction
- **Spec:** P6-SEC-011
- **What:** Regex + built-in patterns (SSN, credit card, email, phone). Confirm-before-apply list.
- **Depends on:** P6.D1.

### P6.D3. `[ ]` Metadata cleaning
- **Spec:** P6-SEC-012
- **What:** Toggle-able: metadata (author/creator/producer/custom), hidden text, comments, attachments, bookmarks, form data, embedded files.
- **Depends on:** none.
- **Touches:** `src-tauri/src/pdf/clean.rs` (a COS transform, not `security/`).
- **Test:** `src-tauri/tests/clean.rs`, against a new
  `tests/fixtures/basic/metadata.pdf` that plants a marker string in each of the
  seven categories. The tests assert the **marker is absent from the saved
  bytes**, not that the key was unset — the latter passes against the obvious
  bug (detaching a reference and leaving the object behind).
- **In place, not on export**, unlike C1/C2: you want to see the comments go and
  you want Undo if you cleaned too much. Byte-snapshot inverse, so undo lasts
  until the file is saved and reopened.
- **Two decisions worth knowing:**
  - *Metadata is two stores.* `/Info` **and** the XMP `/Metadata` packet. The
    fixture puts the same author in both, because clearing only `/Info` is the
    common way a "cleaned" file still names its author.
  - *"Form data" is not "the form".* Values are cleared, the fields stay
    fillable. `/AP` goes with the value — an appearance is a picture *of* the
    value.
- **Hidden text is the sharp edge.** Invisible text (`3 Tr`) is how a scanned
  page is searchable, and P7 will produce exactly such layers. The toggle is off
  by default and the dialog says what it costs; it is not a defect that a
  cleaned scan stops being searchable.
- **Not covered:** hidden *layers* (optional content groups), which the spec line
  does not name. Revisit if a real document turns one up.

## Suggested order

P6.A1 → P6.C1 → P6.C2 → P6.C3 → P6.D3 → P6.A2 → P6.A3 → P6.A4 → P6.B1 → P6.B2 → P6.A5 → P6.D1 → P6.D2

Encryption and metadata cleaning (Track C, D3) land early because they
have no dependency on the signature library and immediately add
demonstrable value. Signing comes after.
